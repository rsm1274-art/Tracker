## What shipped

Added a "Corrections Required" status to the compliance dashboard, replacing the
On-Schedule/Overdue indicator on whichever milestone (Action Plan, 3-Month, or
6-Month) it applies to.

Went through two iterations as the data model came into focus:

1. **First pass** — built against `Anonymized_Data_Corrections.csv`, which has a
   `Pending Corrections` Yes/No column on the same row as an AP/3M/6M task type.
   Per-milestone override + amber pill/badge + filter option, reusing the
   already-defined-but-unused `--warning` color token.
2. **Correction** — the real export doesn't have that column. Corrections arrive
   as their own **Task Type** row ("Correction(s) Required") with their own Due
   date and Completed date, same as Action Plan/3-Month/6-Month rows. Reworked
   detection to key off Task Type instead of a boolean column, and renamed the
   status label from "Pending Corrections" to "Corrections Required" to match
   source terminology.

## Key design decision (user-confirmed)

The source data doesn't say which milestone a "Correction(s) Required" row
corrects. Resolved via `AskUserQuestion`: it supersedes whichever milestone is
**currently active** for that incident — the earliest one not yet completed, or
the last one if all are complete. This mirrors the existing Extended-assessment
supersede pattern (`threeExt`/`sixExt`) already in the codebase.

## Where the logic lives

- `processImportedData` (long-format branch): captures `corrDue`/`corrComp`/
  `corrCompVal` from any Task Type containing "correction", then after Extended
  promotion, picks the active milestone (earliest due date among AP/3M/6M with
  no completion date, else the last one) and overwrites that slot's due/comp/
  compVal, setting `apCorr`/`threeCorr`/`sixCorr`.
- Status assignment (`compiledData` map): if `apCorr`/`threeCorr`/`sixCorr` is
  true, status is forced to `'Corrections Required'` instead of running through
  `getTaskStatus`'s date math — it's a workflow state, not a schedule condition.
- Rendering reuses the existing `renderSubBadge`/pill machinery — amber via
  `--warning`, `.pill.warning`, `.bar-seg.warning` (added, previously unused).
- Filter dropdowns (AP/3M/6M) got a `Corrections Required` option; `gk()` in
  `applyFilters` maps the new status to it.
