What This Is

A single HTML file — no server, no install — that turns an Alert / PEP routing export into a compliance dashboard. Drop in a CSV or XLSX; it pivots the rows into one record per incident (ISB #), works out each incident's status, and gives you charts, a sortable grid, reviewer stats, and CSV/print exports.

Offline by design. Everything — parsing, date math, charting — runs in the browser with no network calls. The badge in the header reads Native Offline Engine for that reason.
01

Getting Data In

Drop a .csv or .xlsx file on the importer (XLSX reads the first sheet only). The importer auto-detects which of two shapes your export uses by checking for a Task Type column.

Long Format Wide Format

Long Format — one row per task, grouped by ISB #

Detected when a header contains task type. All rows sharing an ISB # are grouped; each row's Task Type text is matched by substring (case-insensitive) to sort it into a milestone:

MilestoneMatches Task Type containing…
Action Plan"action plan" / "actionplan"
3-Month Assessment"3-month" / "3month" / "3 month"
6-Month Assessment"6-month" / "6month" / "6 month"
Corrections Required"correction"
Extension Applied"extension"

A Task Type containing "extended" (e.g. Extended 3-Month Assessment) is captured separately and then promoted over the plain 3-Month or 6-Month row — the assessment's Due/Completed dates become the extended ones, and the original dates are kept only for the EXT tag's tooltip. Corrections Required and Extension Applied have no Extended variant.

The reviewer shown as Last Routing is whichever row has the latest Route: Sent Date + Route: Sent Time for that ISB — not simply the first or last row in the file.

Wide Format — one row per ISB

Used when no Task Type column exists. Each milestone's Due/Completed date is read from its own pair of columns, matched against a list of header aliases, e.g. for Extension Applied: extension applied due extension due task: due date (extension applied) and extension applied completed extension completed task: completed date (extension applied). This shape has no Extended-assessment columns, so 3-Month/6-Month extensions never appear here.

Header aliases the importer already knows

FieldRecognized headers (either format)
ISB #isb #, isb number, isb, incident isb, incident isb #
Workstationworkstation, unit, org: workstation, inc: org: workstation
Reviewerreviewer, route: reviewer, current reviewer
Date Createdcreated date, date created, inc: created date
Date Sent to Fielddate sent, date sent to field, inc: date sent to field

Matching is by substring, lower-cased, whitespace-collapsed — column order and extra columns never matter. Dates accept MM/DD/YYYY text, ISO strings, or raw Excel serial numbers.

The Five Milestones

Every incident is tracked against up to five milestones, always in this order:

1Action Plan — the initial corrective plan.
23-Month Assessment — first follow-up review.
36-Month Assessment — second follow-up review.
4Corrections Required — a reviewer sent a submission back for rework.
5Extension Applied — a due date was formally extended.

The overall status shown on the collapsed record row is one of five labels:

Note the wording split: milestone badges use Complete for a finished task, while the overall record status uses the plain On-Schedule/Overdue/Corrections Pending/Extension Applied vocabulary — they're read from different logic (see next section).

04

Overall Status Logic

This is the part worth memorizing — it's the rule that decides which single badge represents an incident with five separate milestones, and it explains why an "Extension Applied" or "Corrections Pending" row sometimes doesn't show the label you expected.

1 An open Corrections Required task (no completed date) always wins — regardless of any other milestone's due date. Shown as Corrections Pending.
2 Otherwise, sort every tracked (non-N/A) milestone by due date, earliest first — ties break Action Plan → 3-Month → 6-Month → Corrections → Extension.
3 The earliest incomplete milestone in that order drives the label. If it's Extension Applied, the record reads Extension Applied; otherwise it shows that milestone's own On-Schedule / Overdue status.
4 If every tracked milestone is completed, the record shows the last (latest due date) one's own status — never the literal "Extension Applied" or "Corrections Pending" label, even if that milestone was the last one completed.
5 If no milestone has a due date at all, the record reads N/A — unless an Extension Applied task was recorded with no due date and no completion, in which case it still reads Extension Applied.
Why a row doesn't show "Extension Applied" even though the source data has that task type: the extension task must be both incomplete and the earliest-due unfinished milestone. If the same incident has an open Corrections Required task, or an earlier-due incomplete Action Plan / 3-Month / 6-Month, that takes precedence. And a completed extension is skipped like any finished milestone — it only drives the label while still open.

Charts and KPI tiles use a related but separate helper, getComplianceBucket() — it reduces "Corrections Pending" and "Extension Applied" back down to their own On-Schedule/Overdue value for counting, so those records still count toward compliance rates by their own due date even though the grid shows a neutral label.

Overdue Aging

Buckets every overdue record's days-past-due (measured from the driving milestone's due date — the same one §04 resolves) into 1–30 / 31–60 / 61–90 / 90+ days, plus the single oldest figure. That ISB # is a link: clicking it switches to the Detailed Data Grid, pages to and expands that record, and briefly highlights the row. If the record has since fallen outside the active filters, a notification says so instead of jumping to a dead row.

Milestone Performance

Five stacked bars, one per milestone type, showing on-schedule vs. overdue rate independent of which milestone is currently driving the overall status — this is where an otherwise-hidden Corrections or Extension rate becomes visible.

06

Detailed Data Grid

A sortable, paginated table — ISB #, Workstation, Last Routing, Date Sent to Field, and the overall Status pill. Click any row to expand it into the five milestone badges from §02.

  • Click a column header to sort by it; click again to reverse.
  • Page size is adjustable (10 / 25 / 50 / 100 rows).
  • Expansion state is remembered per ISB # while filtering, and determines what the Filtered CSV export includes for that row — see §09.
07

Reviewer Performance

One row per reviewer: total incidents, on-schedule count, overdue count, compliance rate — each incident counted once by its getComplianceBucket() value, attributed to whichever reviewer is on the most recent routing event (see §01). Sortable by any column.

Filters & Search

The sidebar filter panel appears once data is loaded, and applies across all three tabs at once.

Workstation / CommandExact workstation match, populated from the loaded file

Typing 3+ letters of "extended" into Search (e.g. ext) also surfaces any record with an Extended 3-Month or 6-Month assessment, on top of the normal field match. Clear Filters resets everything, including sort and page.

09

Exporting & Sharing

Filtered CSV

Every currently-filtered record, one row each, plus a header block recording exactly which filters were active. Milestone due/completed/status columns are populated only for rows you expanded in the grid at export time — collapsed rows export blank there.

Reviewer CSV

The Reviewer Performance table, exported with the same active-filters header block.

Print / PDF

Triggers the browser print dialog; the stylesheet's print rules collapse charts to a single column and tighten spacing for paper.

Export Dashboard

Bakes the currently loaded dataset into a new standalone HTML file, locked in read-only viewer mode — the importer is hidden, and a runtime integrity check every 2 seconds detects any attempt to tamper with the embedded-data lock and blanks the page if it's been altered. Hand this file to someone who needs to see the numbers but shouldn't be able to load a different file over them.

10

vXX_3_3 Changes

What's different in this build relative to the plain On-Schedule/Overdue-only versions:

  • Corrections Pending and Extension Applied added as their own tracked milestones and overall-status labels (§02–§04).
  • The Compliance Trend card was removed from the Overview tab — its month-over-month rate didn't reconcile with the Overall Compliance KPI tile and was retired rather than fixed in place.
  • Workstation Volume & Status now spans the full left column of the Overview grid (vertically, across both chart rows) to fill the space the Trend card left, instead of stretching Overdue Aging horizontally.
  • The Overdue Aging card's "Oldest" ISB # is now a clickable link to that record in the Detailed Data Grid (§05).
  • Export Dashboard's downloaded filename now reads Alert_PEP_Compliance_<date>.html (previously Compliance_Dashboard_<date>.html).
